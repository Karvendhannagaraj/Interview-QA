# Part 1: What is HTTP?

**HTTP = Hypertext Transfer Protocol**

Break the name:

```text
Hypertext  → Web content/resources
Transfer   → Send and receive
Protocol   → Agreed communication rules
```

The most important word is **protocol**.

Imagine you go to a restaurant.

```text
You:
"I want one dosa."

Waiter:
"Order accepted."

Kitchen:
Prepares dosa.

Waiter:
Returns dosa.
```

There is a communication pattern:

```text
Request → Processing → Response
```

HTTP does exactly this:

```text
CLIENT                    SERVER

   │                         │
   │──── HTTP Request ──────►│
   │                         │
   │      Processing         │
   │                         │
   │◄─── HTTP Response ──────│
   │                         │
```

The client can be:

```text
Browser
Mobile application
Frontend JavaScript
Postman
Another backend service
curl
```

The server can be:

```text
Nginx
Apache HTTP Server
Node.js server
PHP application
Java application
Python application
API Gateway
```

HTTP is fundamentally a **client-server request-response protocol**. ([MDN Web Docs][2])

# Part 2: What is actually inside an HTTP request?

Suppose your browser calls:

```text
https://api.example.com/users/10
```

Conceptually, the browser creates something like:

```http
GET /users/10 HTTP/1.1
Host: api.example.com
Accept: application/json
Authorization: Bearer eyJ...
User-Agent: Chrome
```

This request has four major parts:

```text
┌─────────────────────────────┐
│ 1. METHOD                   │
│ GET                         │
├─────────────────────────────┤
│ 2. TARGET / PATH            │
│ /users/10                   │
├─────────────────────────────┤
│ 3. HEADERS                  │
│ Accept: application/json    │
│ Authorization: Bearer ...   │
├─────────────────────────────┤
│ 4. BODY                     │
│ Optional                    │
└─────────────────────────────┘
```

Think of a courier parcel:

```text
HTTP Method  = What action should happen?
URL          = Where should it go?
Headers      = Instructions written on the parcel
Body         = Actual content inside the parcel
```

Example:

```http
POST /users HTTP/1.1
Host: api.example.com
Content-Type: application/json
Authorization: Bearer token123

{
    "name": "Karvendhan",
    "role": "Developer"
}
```

Here:

```text
POST
↓
I want to create something.

 /users
↓
The target resource.

Content-Type: application/json
↓
The body format is JSON.

Authorization: Bearer ...
↓
Here are my credentials.

JSON body
↓
Here is the actual data.
```

That is the anatomy of an HTTP request.

# Part 5: Connection layer

For traditional HTTP/1.1 and HTTP/2, the simplified model is:

```text
HTTP
 ↓
TLS (for HTTPS)
 ↓
TCP
 ↓
IP
 ↓
Network
```

For HTTP/3:

```text
HTTP/3
 ↓
QUIC
 ↓
UDP
 ↓
IP
```

This distinction is important at senior level.

A simplified analogy:

```text
HTTP = The language of the conversation

TLS = Private encrypted room

TCP = Reliable delivery mechanism

IP = Addressing and routing system

Ethernet/Wi-Fi = Physical transport
```

HTTP says:

```text
GET /users
```

TCP is concerned with:

```text
Did the bytes arrive?
Did they arrive reliably?
Should missing data be retransmitted?
```

IP is concerned with:

```text
Which destination address should receive the packets?
```

These layers have different responsibilities.

# Part 6: HTTP vs HTTPS

This is the most important correction:

```text
HTTPS is not a completely different application protocol.
```

A useful simplified model is:

```text
HTTP
```

versus:

```text
HTTP
  ↓
TLS security
```

## HTTP

```text
Browser
   │
   │  GET /users
   │  Authorization: token
   │
   ▼
Server
```

Traffic is not protected by TLS.

Someone able to observe the network path may potentially inspect or manipulate unprotected traffic.

## HTTPS

```text
Browser
   │
   │  🔒 Encrypted traffic
   │
   ▼
Server
```

HTTPS uses TLS to provide three major security properties:

```text
1. Confidentiality
   ↓
   Others cannot simply read the traffic.

2. Integrity
   ↓
   Tampering can be detected.

3. Authentication
   ↓
   The client verifies the server identity
   through certificates.
```

## Comparison

| Area               | HTTP                               | HTTPS           |
| ------------------ | ---------------------------------- | --------------- |
| TLS encryption     | No                                 | Yes             |
| Default port       | 80                                 | 443             |
| Certificate        | No                                 | Yes             |
| Traffic protection | No TLS protection                  | TLS protected   |
| Production use     | Avoid for public sensitive traffic | Standard choice |

# Part 7: Where does TLS happen?

This is a very important infrastructure question.

Common architecture:

```text
Browser
   │
   │ HTTPS :443
   ▼
┌──────────────────┐
│ NGINX             │
│ TLS certificate   │
│ TLS terminates    │
└────────┬─────────┘
         │
         │ HTTP or HTTPS
         ▼
┌──────────────────┐
│ PHP Application  │
└──────────────────┘
```

This is called:

```text
TLS Termination
```

The web server or load balancer may:

```text
1. Receive encrypted traffic
2. Perform the TLS process
3. Decrypt the request
4. Process HTTP information
5. Forward the request internally
```

In another architecture:

```text
Internet
   ↓ HTTPS
Load Balancer
   ↓ HTTPS
Nginx
   ↓
PHP-FPM
```

So when an interviewer asks:

> Where is HTTPS handled?

Do not automatically answer:

> In PHP.

The answer may be:

```text
Load balancer
Reverse proxy
Web server
CDN
API gateway
```

depending on the architecture.

# Part 9: What is an HTTP header?

The easiest deep definition:

> An HTTP header is metadata or an instruction attached to an HTTP request or response.

The body is the **main content**.

Headers describe **how to understand, process, secure, cache, or route that content**.

Car analogy:

```text
CAR

Engine                    = Body / main work
Dashboard information     = Headers
```

The dashboard tells you:

```text
Speed
Fuel level
Engine temperature
Warning indicators
```

It is not the engine itself.

But it gives important information about the engine and car.

Similarly:

```http
Content-Type: application/json
```

says:

> Interpret the body as JSON.

```http
Authorization: Bearer token
```

says:

> Here are the credentials.

```http
Accept: application/json
```

says:

> I prefer a JSON response.

# Part 10: The most important request headers

| Header            | Purpose                   |
| ----------------- | ------------------------- |
| Host              | Target host               |
| Authorization     | Credentials               |
| Content-Type      | Format of request body    |
| Accept            | Preferred response format |
| Origin            | Request origin for CORS   |
| Cookie            | Sends stored cookies      |
| User-Agent        | Client information        |
| If-None-Match     | Conditional cache request |
| If-Modified-Since | Conditional request       |
| Accept-Encoding   | Supported compression     |

Three headers you must deeply understand:

## Content-Type

```http
Content-Type: application/json
```

Meaning:

```text
The data I am sending is JSON.
```

## Accept

```http
Accept: application/json
```

Meaning:

```text
I want JSON back.
```

Difference:

```text
Content-Type
    ↓
What am I sending?

Accept
    ↓
What do I want to receive?
```

## Authorization

```http
Authorization: Bearer eyJ...
```

Meaning:

```text
Here are my credentials.
```

# Part 11: Important response headers

A server may respond:

```http
HTTP/1.1 200 OK
Content-Type: application/json
Cache-Control: no-store
Content-Encoding: gzip
Strict-Transport-Security: max-age=31536000
X-Content-Type-Options: nosniff

{
    "id": 10,
    "name": "Karvendhan"
}
```

Important response headers include:

| Header                      | Purpose                             |
| --------------------------- | ----------------------------------- |
| Content-Type                | Response format                     |
| Content-Length              | Body size                           |
| Content-Encoding            | Compression                         |
| Cache-Control               | Caching rules                       |
| ETag                        | Resource version/fingerprint        |
| Location                    | New or redirected resource location |
| Set-Cookie                  | Store cookie                        |
| Access-Control-Allow-Origin | CORS policy                         |
| Strict-Transport-Security   | Enforce future HTTPS use            |
| X-Content-Type-Options      | Prevent MIME sniffing               |
| Content-Security-Policy     | Browser content restrictions        |
| Referrer-Policy             | Control referrer information        |

# Part 12: Which headers should be added in Nginx or Apache?

Important principle:

> **Do not add every header you find on the internet.**

Headers should match:

```text
Application type
Authentication design
Frontend architecture
CORS requirements
Proxy/CDN architecture
Browser requirements
```

A practical baseline for a typical HTTPS web application is:

```text
Strict-Transport-Security
X-Content-Type-Options
Content-Security-Policy
Referrer-Policy
```

Potentially:

```text
Permissions-Policy
```

Depending on the architecture:

```text
CORS headers
Cache-Control
Forwarded / X-Forwarded-* handling
```

## Nginx conceptual example

```nginx
add_header X-Content-Type-Options "nosniff" always;
add_header Referrer-Policy "strict-origin-when-cross-origin" always;
add_header Strict-Transport-Security "max-age=31536000" always;
```

For CSP:

```nginx
add_header Content-Security-Policy "default-src 'self'" always;
```

But **do not blindly copy that CSP into production**. A real application may use scripts, styles, fonts, images, APIs, analytics, or CDNs from other origins. A badly designed CSP can break the application.

## Apache conceptual example

```apache
Header always set X-Content-Type-Options "nosniff"
Header always set Referrer-Policy "strict-origin-when-cross-origin"
Header always set Strict-Transport-Security "max-age=31536000"
```

The exact configuration depends on enabled modules, server architecture, and whether another layer such as a CDN or load balancer already adds the same headers.

# Part 13: Where should a header be added?

This is a senior-level architecture question.

```text
                    HEADER OWNERSHIP

┌────────────────────────────────────────────┐
│ CDN / LOAD BALANCER                        │
│ TLS, edge caching, forwarding information  │
└─────────────────────┬──────────────────────┘
                      ↓
┌────────────────────────────────────────────┐
│ NGINX / APACHE                             │
│ Transport/browser security headers         │
│ Compression and some caching policies      │
└─────────────────────┬──────────────────────┘
                      ↓
┌────────────────────────────────────────────┐
│ APPLICATION                                │
│ Business-specific headers                  │
│ CORS when dynamic                          │
│ Resource-specific cache policy             │
│ Content-Type                               │
│ Location                                   │
└────────────────────────────────────────────┘
```

A good decision rule:

```text
Infrastructure-wide rule?
        ↓
Nginx / Apache / Gateway

Business-specific rule?
        ↓
Application

Edge-specific rule?
        ↓
CDN / Load Balancer
```

Example:

```text
HSTS for every HTTPS response
→ Web server / edge layer may be suitable

Cache-Control for a private bank statement
→ Application should know the business sensitivity

CORS allowed origin based on tenant
→ Application may need dynamic logic
```
